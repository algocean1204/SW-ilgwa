문제 & 지연 원인

순차 파이프라인 병목 (518초 지연)

문제 상황

15장의 슬라이드, 퀴즈, 노트, 과제, TTS를 단일 흐름으로 순차 요청하여 1강당 518초(8.6분)가 소요되었습니다.

원인

  • 이전 슬라이드 문맥 누적으로 인한 직렬 대기 및 GPU 연산 유휴(Idle) 구간 발생
  • 텍스트 생성이 모두 끝날 때까지 무거운 음성 합성 처리가 직렬로 대기

영향

극심한 대기 시간으로 인한 사용자 이탈 및 서비스 연속성 저해.

해결

vLLM 동시 병렬 생성 및 Plan-First 분리

환경 & 모델 채택

  • Modal B200 GPU, Qwen3.6-27B Dense FP8, vLLM
  • 초당 단가($0.001736/초) 기반으로 120초 연산 시간 정밀 제어

아키텍처 개선

  • Plan-First: Opus 4.6이 커리큘럼당 1회 전체 슬라이드 핵심 개요 선제 기획
  • 1슬라이드 = 1컨텍스트 독립 분할 후 vLLM N-병렬 동시 생성
  • 퀴즈·노트·과제 동시 생성, 음성은 대본 생성 즉시 비동기 큐 위임

결과

동일 생성 범위 기준 518s → 120s로 76.8% 단축 (4.3배 가속).

고가용성 장애 대응 및 트러블슈팅

기획 Opus · 양산 Qwen · 폴백 Sonnet의 3단계 연결과 오디오 float32 정규화 파이프라인을 구축했습니다.

안정성 설계

역할 기반 모델 라우팅 & 대체 회로

기획과 양산의 분리 및 비상 우회로

커리큘럼 전체 기획과 슬라이드 본문 대량 양산의 역할을 분리하고 장애 대응 회로를 구축했습니다.

엔지니어링 조치

  • 커리큘럼 기획 (Planner): Claude Opus 4.6 API (커리큘럼당 1회 호출로 비용 부담 없이 전체 맥락 설계)
  • 대량 양산 (SlideGenerator): Modal B200 GPU (Qwen3.6-27B Dense FP8, vLLM 병렬)
  • 생성 폴백 (Fallback): Qwen 서빙 지연 또는 검증 실패 시 Claude Sonnet으로 자동 절체

상용 초거대 API 단독 호출 대비 약 76%~79%의 연산 비용을 절감하면서 27% 마진을 확보했습니다.

트러블슈팅

TTS 음성 오디오 float32 정규화 파이프라인

문제 상황 (음성 깨짐 및 잡음)

Qwen3-TTS 생성 오디오를 WAV 파일로 변환 시 심한 찌직거림과 음성 깨짐 현상이 발생했습니다.

원인 분석

추론 출력 버퍼의 dtype(float16/비정규화) 불일치 상태에서 soundfile WAV 인코더로 전달되어 16-bit PCM 변환 시 양자화 클리핑(Clipping)이 발생함.

해결책 및 결과

  • 오디오 버퍼를 명시적으로 np.float32로 변환 후 [-1.0, 1.0] 범위로 클리핑 정규화 구축
  • 오디오 왜곡률 0% 달성, 깨끗한 16-bit PCM 고음질 음성 합성 확보

마이크로서비스 경계

Spring과 FastAPI의 책임 분리

수명주기, 장애 영향도, 대규모 비동기 I/O(`asyncio`)와 의존 라이브러리(PyTorch, vLLM)의 특성이 다른 AI 워크로드를 Spring 메인 스레드로부터 완전히 격리했습니다. 인증·결제·유저 상태 관리는 Spring이 전담합니다.

초당 과금 기반 연산 통제

Modal B200 인스턴스의 초당 단가($0.001736/초)를 활용하여, 1개 강의 생성 시 필요한 연산 시간(120초)에만 비용이 발생하도록 설계하여 불필요한 GPU 유휴 비용을 최소화했습니다.
