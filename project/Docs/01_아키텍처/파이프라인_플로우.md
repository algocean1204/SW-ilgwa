현행 OCR 구성은 두 갈래다. ①c 교재·범용 PDF는 OCR_V1(Marker 1차 추출 → 품질 게이트 → 걸린 페이지만 MinerU 재추출 + Kanana-2 교정 → BGE-M3 Dense+Sparse 임베딩 → Qdrant `ocr_v1_chunks`)로, ①a 과제 채점은 Sonnet 4.6 VLM 직접 처리(OCR 레이어 없음)로 한다. 상세는 [`AI_파이프라인_설계.md`](./AI_파이프라인_설계.md).

주요 파이프라인을 데이터 흐름 관점에서 적는다. 단계마다 (1) 어떤 시스템 컴포넌트가 (2) 어떤 AI를 (3) 어떤 형식의 데이터로 호출하는지 따라갈 수 있게 썼다.

## 아키텍처 근거

> FastAPI가 모든 AI 진입점을 맡는다. LangGraph 같은 에이전트 프레임워크를 FastAPI 레이어에 붙이기 쉽게 하려는 것이다. Modal GPU는 LLM(Qwen3.6-27B FP8)·TTS(Qwen3-TTS)·ASR(Whisper V3 Turbo)·임베딩(BGE-M3·reranker)·OCR 교정(Kanana-2)에 쓴다.

### OCR / 채점 플로우 개요 (2026-04-19 Dual-path)

#### Path A: ①c 교재·범용 PDF OCR (OCR_V1)
```
Client → Spring → S3 → FastAPI (POST /api/ocr/v1/ingest)
                            │
                Marker 1차 추출
                            │
                4-메트릭 품질 게이트
                (임계값 미달 페이지만 MinerU 재추출 + Kanana-2 교정)
                            │
                BGE-M3 Dense(1024d) + Sparse 임베딩
                            │
                RRF(k=60) + BGE-Reranker-v2-m3
                            │
                    Qdrant ocr_v1_chunks 색인
```
> ①b(PaddleOCR-VL-1.5 Modal A10 + 전 페이지 Kanana-2 후처리) 경로는 2026-05-21에 폐기했다.

#### Path B: ①a 과제 채점
```
Telegram 웹훅 → FastAPI
                    │
                Sonnet 4.6 VLM 직접 처리
                (이미지/PDF → 이미지+텍스트 맥락 직접 이해)
                    │
                채점 결과 → Spring 콜백 → Telegram DM 회신
```
- OCR 레이어가 없어 Sonnet API 비용만 든다.

> CPU PP-OCRv5 ONNX 경로는 2026-04-19에 폐기했다.

## 2. 플로우 1: OCR

OCR 진입점은 두 가지다.
- 1a. 과제 OCR: 사용자가 하루 1회 과제 사진을 올리면 단건 처리한다
- 1b. 참고 도서 OCR: 사용자가 책을 올리면 수백 페이지를 배치 처리한다 (현행은 1c OCR_V1)

### 2.1 1a. 과제 채점 — Sonnet 4.6 VLM 직접 처리 (2026-04-19 변경)

> 2026-04-19 변경: 기존 PaddleOCR ONNX OCR 경로를 제거했다. 과제 이미지/PDF는 Sonnet 4.6 VLM이 직접 처리하고 OCR 레이어는 없다.

트리거: Telegram 웹훅이 학생 파일 제출을 감지. AssignmentGrader 내부에서 이미지/PDF 분기 시 처리.
반환 형식: `D_JSON_GRADE` (채점 결과)

```
[React] Telegram: 학생이 과제 파일 제출 (이미지/PDF)
    ↓
[CPU] Spring Boot → FastAPI 웹훅 라우터

[CPU] FastAPI AssignmentGrader
    ├─ S3 GET: 파일 바이트 로딩
    ├─ [.pdf]  pypdfium2 텍스트 레이어 우선 추출 (CPU only, ₩0)
    │           └─ 텍스트 레이어 없는 페이지: 이미지로 변환 → VLM 경로
    ├─ [이미지/.pdf 이미지 페이지]
    │           ↓
    │   [외부 API] Anthropic API: Sonnet 4.6 (VLM 직접 처리)
    │       call: anthropic.messages.create(
    │           model="claude-sonnet-4-6",
    │           messages=[{
    │               "role": "user",
    │               "content": [
    │                   {"type": "image", "source": {"type": "base64", "data": img_b64}},
    │                   {"type": "text", "text": rubric_prompt}
    │               ]
    │           }]
    │       )
    │       [시간] ~3~5초 (이미지 토큰 포함)
    └─ 채점 결과 → AssignmentGrader → WeakConceptLinker (오답 시)
    ↓ [D_JSON_GRADE]

[CPU] FastAPI → Spring Boot 콜백 (POST /internal/submissions/{id}/ai-result)
[CPU] Telegram DM 회신 (점수 + 해설)
```

#### 산출물 스펙

- `score: float`, `feedback: str`, `weak_concepts_delta: list[ConceptRef] | None`
- overlay PDF 없음. OCR JSON 없음 (VLM 직접 채점).
- 구현 위치: backend-fastapi 직접 구현. 샌드박스 스킵.

DB 변화: 없음 (Spring 콜백으로 저장)
S3 변화: 없음
비용: Sonnet 4.6 VLM 호출 비용 (이미지 토큰 포함). OCR 별도 비용 없음.

### 2.3 1c. OCR_V1 LangGraph Pipeline — 현행 단일 OCR 경로

> 2026-04-23 추가, 2026-05-21 승격: `Test_FastAPI_Module/OCR_v1/` 샌드박스 구현을 마치고 `backend-fastapi/app/modules/OCR_v1/`으로 옮겼다. ①b 경로를 대체한 현행 교재 OCR 경로다.

트리거: 관리자 또는 외부 시스템이 PDF를 OCR_v1 엔드포인트(`POST /ocr_v1/ingest`, port 8005)로 업로드.
반환 형식: `{"embedded_count": int, "collection_name": str, "pipeline_status": str}`

#### 전체 8-Stage 데이터 플로우

```
[CPU] FastAPI OCR_v1 SubApp (port 8005)
    POST /ocr_v1/ingest
    Body: multipart/form-data (pdf_file)
    ↓ [pdf_bytes, pdf_filename]

[Stage 1: classify_pdf] — CPU only
[CPU] OCRv1Pipeline.ingest() → LangGraph graph.invoke()
    ├─ pypdfium2 / pdfminer 텍스트 레이어 감지
    ├─ 페이지별 이미지 변환 → image_ratio 계산
    └─ 산출: list[PageClassification]
       {page_num, type: "born-digital"|"scanned"|"mixed",
        has_text_layer: bool, image_ratio: float, confidence: float}
    ↓ [OCRPipelineState.classifications]

[Stage 2: extract_base] — Marker(marker-pdf)
[CPU] MarkerEngine.extract(pdf_bytes, pages, force_ocr=False, use_llm=False)
    ├─ marker-pdf 라이브러리 호출
    └─ 산출: list[PageExtraction]
       {page_num, markdown: str, tables: list[str], formulas: list[str]}
    ↓ [OCRPipelineState.extractions]

[Stage 3: llm_correct] — 선택적 LLM 교정
[CPU] 환경변수 OCR_V1_MARKER_USE_LLM_MODEL 값이 있을 때만 실행
    ├─ 표·수식 오류가 있는 페이지만 선별
    └─ 지정 모델로 교정 요청
    ↓ [OCRPipelineState.extractions (교정 반영)]

[Stage 4: quality_gate] — 4-메트릭 품질 평가
[CPU] 품질 평가 모듈 (quality/ 하위 6개 서브모듈)
    ├─ char_corruption: 문자 손상률 계산 (가중치 30%)
    ├─ reading_order: 읽기 순서 일관성 (가중치 25%)
    ├─ table_integrity: 표 구조 무결성 (가중치 25%)
    ├─ formula_preservation: 수식 보존률 (가중치 20%)
    └─ aggregate: overall = 가중합

    임계값 검사:
    overall ≥ 0.70
    char_corruption ≤ 0.05
    table_integrity ≥ 0.80
    formula_preservation ≥ 0.90
    reading_order ≥ 0.85

    route_after_quality() 결과:
    ├─ "pass"     → 전 페이지 임계값 통과
    ├─ "partial"  → 일부 페이지 실패 (passed_pages + failed_pages 분리)
    └─ "fail_all" → 전 페이지 실패
    ↓ [OCRPipelineState.quality_scores, passed_pages, failed_pages]

[Stage 5: fallback] — MinerU 폴백 재추출 ("partial" 경로만)
[CPU] MinerUEngine.extract(pdf_bytes, pages=failed_pages, force_ocr=True)
    ├─ magic-pdf 라이브러리로 실패 페이지만 재처리
    ├─ 최대 1회 재시도 (OCR_V1_MAX_QUALITY_RETRIES=1)
    ├─ Kanana-2 교정 (MinerU로 다시 뽑은 페이지만. 전 페이지 적용 시 CER 0.437로 악화)
    └─ 결과를 passed_pages 결과와 병합
    ↓ [OCRPipelineState.fallback_extractions]
```

### 4.1 3a. 과제 생성 (문항 선택 + 문제 생성)

트리거: 과외 완료 (`POST /assignments/generate` 호출).
반환 형식: `D_JSON_ASSIGNMENT` (과제 메타 + 문항 배열 + selectionSignals)

#### 3축 가중치 시그널 집계

출제 파트를 결정하기 위해 PostgreSQL에서 아래 3가지 집계 쿼리를 실행한다.
집계 비용은 과제 생성 1회당 쿼리 3회로, 부하는 무시 가능 수준이다.

```sql
-- 질문밀도: 슬라이드별 QA 발생 횟수
SELECT slide_id, COUNT(*) AS qa_cnt
FROM qa
WHERE user_id = $1 AND slide_id IS NOT NULL
GROUP BY slide_id;

-- 되감기 비율: play 이벤트 대비 seek+direction=back 이벤트 비율
SELECT slide_id,
       COUNT(*) FILTER (WHERE event_type = 'seek'
                          AND payload->>'direction' = 'back')::float
       / NULLIF(COUNT(*) FILTER (WHERE event_type = 'play'), 0) AS rewind_ratio
FROM playback_event
WHERE user_id = $1
GROUP BY slide_id;

-- 오답률: 개념별 누적 오답 비율
SELECT concept_id,
       SUM(wrong_count)::float / NULLIF(SUM(attempt_count), 0) AS wrong_ratio
FROM quiz_concept_stat
WHERE user_id = $1
GROUP BY concept_id;
```

#### 가중합 및 출제 후보 선별

```
입력: user_id, lesson_id / chapter scope
  ↓
[단계 1: 집계]
[DB 읽기] DB SELECT — 질문밀도 / 되감기 비율 / 오답률 쿼리 3종 병렬 실행

[단계 2: 정규화 + 가중합]
[CPU] FastAPI
    각 시그널 0~1 min-max 정규화
    score(slide) = α × qa_cnt_norm + β × rewind_ratio_norm + γ × wrong_ratio_norm
    (기본값 α=0.4, β=0.3, γ=0.3 — weightOverride 요청 시 대체)
    질문 없는 슬라이드: α 기여분 0 → 자연 탈락

[단계 3: 상위 슬라이드 선별]
    score 기준 상위 N개 슬라이드/개념 선별
    (N = questionCount 기반 자동 결정)
    → selectionSignals.topSlides 확정
```

```
pending ──► queued_for_batch ──► ocr_running

                         ▼
                        done
                         │  (콜백 5회 실패)
                         ▼
                       failed ──► DLQ 적재, 운영자 개입
```

#### 재제출 (submission_retry)

- `pending` 또는 `queued_for_batch` 상태일 때만 허용
- `ocr_running` 이후 재제출 차단
- 재제출 이력 → `submission_retry` 테이블 (retry_no 1부터 증가)
- **첫 제출(official)이 공식 점수** — retry는 피드백 참고용
- 배치 시 `officialFileUrl` + 최신 `retryFileUrl` 함께 채점 대상으로 전달

DB 변화: `submission` 상태 전이 + `official_score`/`official_feedback`/`official_ai_confidence` 저장, `user_weak_concepts` UPDATE
S3 변화: `assignments/{user_id}/{submission_id}/official.{ext}` (제출 시 저장)
##### 비용

- 과제 이미지 판독: Sonnet 4.6 VLM 호출 비용에 포함 (별도 OCR 과금 없음). 2026-04-19 이전 ONNX CPU 경로는 ₩0 추가 과금이었다
- Sonnet 채점: ₩56
- Haiku 병합: ₩3
- S3 PUT: ₩0.5 (제출 시 이미 발생)
- **합계: ~₩60 / 과제**

총 시간: 배치 내 처리 warm 6~8초/건 (실시간 대기 없음, 배치 완료 후 콜백 수신)

## 5. 플로우 4: 챕터 생성

> 이 절의 단계 구성, GPU 이름, 비용은 초기 설계 추정치다. 최종 구성은 Qwen3.6-27B FP8·vLLM(Modal B200, 슬라이드 8슬롯 병렬)이고, 실측 결과(1강 120초, 1강당 총 과금 $0.38)는 [`메인강의생성_실전검증.md`](../05_실측/메인강의생성_실전검증.md)에 있다.

서비스의 핵심 플로우. **Planner-Executor 패턴**으로 구성:
- **Planner** (Opus 4.6): 1강당 1회 (커리큘럼 설계), 판단 담당. 지시서 `D_JSON_PLAN` 생성.
- **Executors**: 지시서를 받고 실행만. 모델 tier별로 분담.

### 트리거

```
① 코스 시작 시점: 자동으로 챕터 1, 2 생성
② 학생이 챕터 N 퀴즈 완료: 챕터 N+2 자동 생성
③ 수동: 사용자가 "다음 챕터 준비" 버튼
```

## 6. 부록 A: Cold Start 완화 포인트

Modal 컨테이너의 cold start를 최소화하기 위한 3가지 전략이다. 아래 GPU 이름(A10, H100)과 `qwen_asr` 컨테이너는 초기 설계 기준이다. 최종 구성은 §1.4 표를 따른다.

### A1. GPU Snapshot 활성화 (필수)

모든 Modal 컨테이너에 다음 설정:
```python
@app.cls(
    gpu="A10",  # 또는 H100
    scaledown_window=300,
    enable_memory_snapshot=True,
    experimental_options={"enable_gpu_snapshot": True},
)
```

- 첫 5회 호출: snapshot 만드는 중 → cold start 15~20초
- 안정화 후: cold start 3~5초
- **출시 전에 각 컨테이너 5~10회 warmup 호출 필요**

### A2. 예측 워밍 (핵심)

사용자 행동 신호를 미리 감지해서 컨테이너 예열:

| 사용자 행동 | 예열 대상 컨테이너 |
|---|---|
| 챕터 페이지 열기 | `qwen_asr` (음성 질문 대비), `qwen_tts` (음성 답변 대비) |
| 앱 홈 진입 (오전) | — (과제 판독은 Sonnet VLM API라 cold start 없음) |
| "다음 챕터 준비" 클릭 | `qwen_llm` H100 |
| 책 업로드 시작 | `ocr-bge-m3` |

구현:
```python
async def warmup_container(app_name: str):
    asyncio.create_task(
        modal.Function.from_name(app_name, "ping").remote.aio()
    )

@app.route("/chapters/{id}/open")
async def open_chapter(id):
    warmup_container("qwen_asr")
    warmup_container("qwen_tts")
    return chapter_data
```

### A3. 주기적 핑 (선택)

활성 시간대(19:00~23:00)에만 3분 주기 핑:
```python
@app.function(schedule=modal.Cron("*/3 19-23 * * *"))
def keep_alive():
    # 각 A10 컨테이너에 ping 호출
    ...
```

- 주의: H100(`qwen_llm`)은 제외 — 무료 크레딧 빠르게 소진됨
- A10 2개만 적용 (`qwen_asr`, `qwen_tts`): 월 ~₩8,000 추가
  (기존 `qwen_vl` A10은 제거했다. 과제 판독은 Sonnet VLM, 교재 OCR은 OCR_V1에서 한다)
