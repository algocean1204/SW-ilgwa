벤치마크 및 폐기

단일 OCR 경로의 수식·표 파손 실측

실측 수치 및 판정

초기 후보였던 CPU ONNX(PP-OCRv5)는 문자오류율(CER) 48.8%(빈 출력 8.3%), PaddleOCR-VL 단독 경로는 페이지 CER 75.9%(페이지당 10.39초)로 측정되어 단독 배포 불가로 판정했습니다.

원인 분석

  • 전공 서적의 다단 레이아웃에서 문단 읽기 순서가 뒤섞임
  • LaTeX 수식 기호와 표 경계가 깨진 채 청킹되어 벡터 검색 품질 저하

최종 아키텍처

품질 게이트 이중 추출 + BGE-M3 하이브리드 검색

입력 경로 분리: 참고 도서 색인 vs 학생 과제 제출

500~1,000페이지 분량의 참고 도서는 텍스트 레이어(`pypdfium2`) 우선 추출 후 래스터화가 필요한 페이지만 하이브리드 OCR 파이프라인으로 색인하고, 학생이 제출하는 단일 과제 이미지·PDF는 별도 OCR 없이 멀티모달 모델(Sonnet VLM)이 직접 판독하도록 분리해 불필요한 GPU 호출을 제거했습니다.

자유 생성 시 출력 구조 편차 및 사실 오류

문제 상황

모델에게 슬라이드와 문항 구조 전체를 자유롭게 생성하게 하면 요청마다 구성과 난이도가 달라지고, 설명이나 코드 결과에 오류가 섞였습니다.

해결 원칙

프레임·시각 타입·난이도는 코드가 Plan-First로 고정하고, 생성된 JSON은 사실·논리 검증 노드를 거쳐 오류가 지적된 필드만 선별 교정합니다.

해결

JSON 스키마 {{빈칸}} 고정 & 내용 검증 루프

구현 상세

고가용성 설계

역할별 모델 분리 & 다단계 자동 폴백

계층형 라우팅

  • 기획(Planner): Claude Opus 4.6 (커리큘럼당 1회 호출로 전체 흐름 고정)
  • 본문 양산: Modal B200 Qwen3.6-27B Dense FP8 (vLLM 병렬 서빙)
  • 질의응답·채점: Claude Sonnet 4.6 (보조 필터 Haiku 4.5, 후처리 Kanana 2.1B)

장애 우회 및 토큰 클램프

주 경로(Modal GPU) 타임아웃·오류 시 Gemini → Claude Sonnet / OpenAI 순으로 자동 전환하며, 모델 간 최대 출력 토큰 차이로 인한 400 오류를 막기 위해 max_tokens=16384 클램프를 적용했습니다.

트러블슈팅

TTS 오디오 float32 정규화 및 비동기 큐 분리

문제 및 원인 (음성 깨짐 현상)

Qwen3-TTS 추론 출력 텐서(float16·비정규화 범위)를 그대로 soundfile PCM_16 WAV 인코더에 전달하면서 비트 깊이 변환 오버플로와 클리핑 잡음이 발생했습니다.

해결 및 결과

  • np.clip(audio.astype(np.float32, copy=False), -1.0, 1.0) 전처리로 클리핑 잡음 제거
  • 참조 음성과 참조 문장을 함께 고정해 화자 유사도 0.964~0.976(표준편차 0.0006) 달성
  • 슬라이드 파이프라인은 대본만 voice_script_queue에 넣고 TTS 워커가 비동기 합성

마이크로서비스 경계와 비용 통제 구조

Spring 코어와 FastAPI AI 서버의 역할 분담

인증·결제·코인 차감(원자적 조건부 UPDATE) 등 정합성이 중요한 트랜잭션은 Spring Boot가 전담하고, FastAPI는 VPC 내부망에서 추론·검색·합성 워크로드만 수행합니다. 대용량 5대 산출물 적재는 FastAPI가 asyncpg로 직접 INSERT하고, 채점 완료 이벤트는 3회 재시도 웹훅으로 Spring에 콜백합니다.

비용 구조: 상용 단독 대비 76~79% 절감

전체 흐름을 설계하는 기획(Opus 4.6 1회 호출)과 대량 본문 양산(Modal B200 Qwen3.6-27B 초당 과금 서빙)을 분리해, 상용 초거대 API 전량 호출 대비 모델 연산 비용을 76~79% 절감하고 약 27%의 운영 마진을 확보했습니다.
